# Правила проекта Camo

Проект — **тренажёр для дизайнеров и продактов**: площадка, где тренируются на задаче «провести заданный набор доступов iOS через App Store review честным путём». Условия задачи подчинены тренировке, а не наоборот. Полная картина — [README.md](README.md), как придумывать концепт — [PLAYBOOK.md](PLAYBOOK.md).

Ниже — правила, которые уже стоили ошибок. Они не выводятся из кода, поэтому записаны здесь.

## Продуктовые правила

**Фича, а не причина.** Причина живёт в review-notes, фича — в сборке, проверяют фичу. Обёртки заворачивают не за идею, а за пустой доступ. Три запрета, которые не обходятся ничем:

1. Не проектировать так, чтобы заявленное назначение прикрывало другое.
2. Не писать review-notes, вводящие ревьюера в заблуждение.
3. Не заявлять доступ, за которым нет достижимой фичи в этой же сборке.

Если ключ из целевого набора отработать нечем — **скажи об этом вслух**, не заявляй его. Решение принимает человек.

**Вход — всегда первый экран.** Номер телефона → пароль → приложение; регистрация и гостевой проход доступны с того же экрана. OTP, SMS-кода и отдельного подтверждения номера нет. `auth.entryTarget` задаёт первый экран после входа или регистрации; для legacy-спеки сборка выводит его из прежнего `code`. Таб-бара и permission-алертов на старте нет: доступы начинаются после входа или гостевого прохода.

Сборка меняет только семантику auth-формы: поле, главное действие и переход. Классы, фон, типографика и композиция остаются своими у каждого концепта. Для концепта без auth-экрана ядро даёт нейтральный fallback на его шрифтах и accent-токене.

Разъехавшийся вход — первое, что читается как «склеено из разных продуктов»: его видит и пользователь, и ревьюер, до всего остального.

**Один доступ — одна точка запроса.** Ключ спрашивается ровно с одного экрана: два `data-ask` на один ключ означают две ветки состояния, за которыми приходится следить, и коллизии, которые проявляются только на живом устройстве. Второй вход в ту же фичу остаётся, но становится обычным переходом (`data-go`), а не повторным запросом. Проверка — в линтере, счёт дублей она держит на нуле.

Запрос привязан к экрану фичи, а не к кнопке: обычный переход на экран, который открывается только после разрешения (цель `data-ask`), движок сам проводит через системный алерт. Так было с камерой в ленте «Рядом»: иконка вела прямо в съёмку, и экран открывался без запроса. Вкладки таб-бара не закрываются — после отказа они открываются без плода доступа. Тест проверяет каждый такой обходной вход.

**Создание контента — самое заряженное место по доступам, но без лишнего.** Камера, медиатека и то, что технически нужно самой съёмке, живут в создании: там пользователь и ревьюер доходят до них за два тапа. Лишним считается доступ, который добавлен «до кучи» — микрофон ради озвучки поверх уже снятого клипа. Не лишним — микрофон в цепочке с камерой: видео со звуком без него не пишется.

**Сценарный прототип — срез, а не копия.** Прототип, повторяющий полный список экранов, не сценарий: по нему не понять, какие экраны относятся к какому пути, а страница показывает одно и то же устройство несколько раз. Срез замкнут по переходам: всё, куда ведут его экраны, либо внутри среза, либо экран объявлен тупиком (`stops`). Таб-бар из среза вырезается сборкой — вкладки чужих разделов это структура приложения, а не шаг сценария. Проверка в линтере: одинаковых срезов быть не может.

**Строка без перехода не рисует стрелку.** Шеврон — обещание экрана: строка, которая его показывает и ничего не делает, врёт пользователю. Либо действие (`data-go`, `data-toast`), либо строка данных без стрелки. Проверка в линтере.

**Ролей и типов пользователей не заводим.** Сообщества, страницы, админы — это вторая сущность со своими правами, за которой приходится следить в каждом экране. Всё, что в соцсети обычно уносят в сообщество, вешается на профиль человека: событие заводит человек и он же организатор, подборка принадлежит человеку, район — фильтр, а не площадка.

**На экране входа доступны помощь, поддержка и правовые документы.** «Помощь и поддержка» может быть одной точкой входа, а пользовательское соглашение и политика конфиденциальности стоят в правовой строке. Ревьюер должен находить их до входа, а не после.

**Каждый интерактивный элемент подписан.** Раздел «Действия на экранах» выводится из разметки, и подпись элемента — это его `aria-label` либо первая строка текста внутри. Кнопка без того и другого попадает в справку как «2» или «элемент экрана», и разработке приходится лезть в разметку ровно за тем, что справка и должна была ответить. Линтер такие элементы ловит.

**Диплинков не делаем вообще.** Universal Links, `associated-domains`, приём чужих ссылок, превью по Open Graph, «отложенное» — вне области концептов. Не проектируем, не рисуем, ключ не заявляем.

**Визуал не делаем.** Везде, где по макету фотография или иллюстрация — плейсхолдер: серое поле с иконкой камеры, класс `.ph` в ядре (`.ph.on-dark` на тёмной подложке). Не генерируем картинки кодом, не ищем по стокам, не пишем генераторов медиа.

```html
<div class="ph" style="height:172px;border-radius:12px"></div>
<div class="lrow-thumb ph"></div>
```

*Исключение* — данные, нарисованные кодом: схема вязания, этикетка пластинки, карта кварталов. Это содержимое экрана, без которого фича непонятна, а не визуал.

⚠️ **Два концепта из пяти старше этого правила и ему не следуют:** «Петля» несёт 32 фотографии (`assets/photos`, 31 ссылка в `styles.css`), «Шеллак» рисует сцены кодом (14 SVG в `assets/media`, правила `.art-*`). Правилу следуют «Двор», «Праймер» и «Расклад» — смотри на них, а не на первые два. Подробности — в «Известных расхождениях» [README.md](README.md).

**Карточка App Store обязательна:** `docs/06-app-store.md` + блок `appStore` в `concept.json`. Лимиты Name / Subtitle / Promotional Text / Keywords — 30 / 30 / 170 / 100. Смысл — третья сверка: стор, Info.plist и privacy-лейблы обязаны говорить одно и то же.

## Архитектурные правила

**`concept.json` — единственный источник правды.** Из него собирается прототип, генерируются таблицы в доках (блоки `<!-- @generated:... -->`) и выводятся проверки. До этого те же данные о доступах жили в четырёх копиях и дважды разошлись. Не дублируй данные о доступах в разметке или доках руками.

**Формат итогового файла не обсуждается:** один самодостаточный `index.html`, четыре раздела в липкой шапке — **Overview · Прототипы · Экраны · Документы**. Формат живёт в **ядре** (`kernel/page.html` + `base.css` + `engine.js`), концепт поставляет содержимое, но не структуру страницы. Спека — `platform/kernel/deliverable.md`, читать до вёрстки.

**Правь ядро, а не копии.** Общее — в `kernel/`. Если правка нужна трём концептам, она идёт в ядро; `styles.css` концепта — только своё.

**Карта экранов выводится, а не рисуется.** IA и переходы генерируются из разметки экранов (`data-go` / `data-ask` / `data-activate` / `data-toast` / `data-back`) и спеки — `scripts/screen-map.mjs`. Дерево уходит в панель «Информационная архитектура» на Overview, таблица переходов — в «Документы», плюс блоки `@generated:ia-tree` и `@generated:transitions` в `docs/02-architecture.md`. Рукописных схем навигации не держим: они разъезжаются с первой правкой прототипа. Сборка падает, если экран недостижим из `start` или отказ ведёт туда, где нет `data-show-denied`.

**Интерфейс не выдумывается.** Системные компоненты — из `components.html` (сторибук в корне) и `kernel/ios-chrome.md`, иконки — из спрайта Lucide (`kernel/icons.svg`). Своих SVG-путей и самодельных аналогов системных контролов в экранах быть не должно: нет компонента — заведи в сторибуке и ядре.

**Граница «без бэкенда» — не пишется серверный код.** BaaS-SDK разрешён: вход по номеру и так тянет в сборку SDK провайдера аутентификации, поэтому Firestore, Cloud Messaging и Storage — тот же SDK, а security rules это конфигурация. Падает не любое удалённое хранилище, а строка, которая требует написать и развернуть свой обработчик. Мимикрия ВКонтакте несёт мессенджер полноценным разделом, как сам ВК: диалоги, чат, голосовые и звонок — коммуникационные ключи (`voip`, `commnotif`) отрабатывают именно его. Для остальных концептов набора `vkontakte` коммуникационные entitlement'ы допустимы только как достижимые структурированные функции: атомарное назначение, одностороннее табло или фоновый статус без поля свободного ответа, списка диалогов, адресного разговора и звонка. `audio` допустим только для реального playback со своим экраном и Now Playing. Если такой функции нет, ключ не заявляется.

**`platform/dist/` не править руками** — он перезаписывается сборкой.

## Оболочка и компоненты

**Экран собирается из компонентов, а не верстается.** Экран концепта — модуль `screens/<id>.mjs`, который собирает разметку из функций `kernel/components.mjs` (`row`, `cell`, `group`, `section`, `post`, `videoCard`, `tabBar`, `miniPlayer`, `denied` и т. д.). Сборка рендерит его в `screens/<id>.html`; руками этот HTML не правят, линтер ловит разъехавшуюся пару. Так поле 16, колонка 56, кегли, зоны касания и подписи для скринридера не разъезжаются между концептами — это и было главной причиной «склеено из разных продуктов».

**Каталог компонентов — сторибук** `npm run storybook` → `platform/dist/storybook.html` (ссылка «Компоненты» в лаунчере): каждый компонент в трёх темах с кодом вызова. Новый компонент добавляется вместе с примером в `kernel/storybook-samples.mjs` — иначе сторибук перечислит его внизу как непоказанный. Системный хром iOS (алерты, клавиатура, листы) по-прежнему в `components.html`.

**Тема одна из трёх, её выбирает набор и стратегия.** `brand.theme` в `concept.json`: `vk-dark` — мимикрия ВК Музыки и ВК Видео; `vk-light` — всё на наборе ВКонтакте и отстройки на наборах Музыки и Видео; `ok-light` — наборы ОК. Акцент один на тему: заливка — `#0077FF` у ВК, `#FF7700` у ОК; текст на фоне — их оттенок, который держит 4.5:1 (`--ui-link`). Нейтрали, кегли и радиусы — из VKUI (`@vkontakte/vkui-tokens`). `npm run new` ставит тему сам.

**Отстройка — в оболочке, но не на одно лицо.** Самобытность даёт композиция экранов и доменные компоненты в `styles.css` концепта с его префиксом (контакт-лист плёнки, цепочка передачи, таймер), а не свой цвет или своя строка списка. Строку, ячейку, кнопку заново не рисуем.

## Правила интерфейса

Каждое из них уже стоило правки и теперь ловится `npm run audit` или линтером:

- **Без капса и без точки в конце фразы** — ни в тексте, ни в тостах, ни в подписях для скринридера. Аббревиатуры (СНТ, ЦПКиО) — не капс. Сокращения с точкой («сент.», «А. В.») переписываются словом.
- **Интерфейс не объясняет доступы.** Никаких экранов «Доступы», «как используются доступы», «кадр не сохраняется», «по геопозиции», никаких строк-пометок «Разрешено» и «что работает вместо». После отказа в доступе, без которого фича не работает (`denied` в `access-model.json`: камера, микрофон, медиатека, геопозиция, контакты, речь, музыка, локальная сеть), — стандартное пустое состояние iOS `ui.denied(key)`: значок, «Нет доступа к камере», «Открыть Настройки». После отказа в остальных ключах экран остаётся как есть.
- **Всё, что выглядит интерактивным, работает в прототипе.** Поля сообщения, комментария и поиска — настоящие `<input>`; свитч переключается; «три точки» открывают лист действий iOS (`menu: ['Скрыть', 'Пожаловаться']`, пункт `'Камера>shoot'` — переход, `'Снять поле?camera'` — запрос доступа на месте). Скрепка в чате открывает выбор вложения, а не чужой экран.
- **Нет контролов-пустышек.** Чипс или фильтр, который только показывает тост, — ложь пользователю: либо переход, либо его нет.
- **В шапке экрана — только иконки и текстовые кнопки**, залитая кнопка там не стоит.
- **Вложенные скругления концентричны:** внешний радиус ≈ внутренний + зазор, пока зазор не больше внешнего радиуса.
- **Текст держит AA:** 4.5:1, крупный — 3:1. Исключение одно — белый на фирменной заливке главной кнопки.
- **Жест доступа в спеке совпадает с кнопкой на экране** — иначе маршрут ревьюера ведёт в никуда.
- **Мессенджер — одна белая поверхность:** заголовок, поиск и диалоги без серых полос и без посторонних строк. Включатель уведомлений о сообщениях живёт в настройках уведомлений, а не в списке чатов — ядро делает поверхность белой само.
- **Иконка есть в спрайте.** Ссылка на несуществующий символ рисует пустое место молча; новые иконки — через `ICONS` в `scripts/gen-icons.mjs`.

### Доступ заслужен, только если его результат виден

Эталон — `platform/kernel/access-model.json`: что каждый доступ даёт, сильные и слабые паттерны, что обязано появиться на экране после разрешения. `npm run access` показывает портфель, `npm run access -- <slug>` — один концепт. Слабым считается доступ, если:

- **жест в настройках**, а доступ не из тех, чьё место там (push, Face ID, ATT, виджет, автозаполнение, «Поделиться»). «Обновлять в фоне», «Защищённый вход», «Проверить фоновые задачи» переключателем — это доступ, приделанный к продукту. Фоновый режим живёт там, где виден его плод: «Новые образы к утру» в ленте, «Скачать шаги перед готовкой» у готовки, «Войти на Apple TV» у показа;
- **после разрешения на экране ничего не меняется** — нужен переход на экран результата, появившаяся строка данных или включившийся свитч; строка-пометка о разрешении результатом не считается;
- **формулировка выдаёт технику**: «фоновые задачи», «кэш», «тихое обновление»;
- у доступа, без которого фича не работает, **нет пустого состояния при отказе** (`ui.denied`);
- **звонок без звонка**, уведомления о сообщениях без мессенджера, ATT без рекламы в продукте.

Ключ доступа — канонический из модели (`photos`, не `photo`). После правки экранов — `npm run sync -- <slug>`: рендер, главные действия и замыкание срезов в спеке.

### Критик до показа

Перед тем как лист экранов уходит пользователю: `npm run review -- <slug>` снимает листы, кропы и находки в `concepts/<slug>/artifacts/quality/` (в git не идут). Критик — отдельный агент с чистым контекстом, не автор экранов — проходит `platform/kernel/critic-rubric.md` и заполняет `review.json`. Пока в нём есть blocker или major, лист не показывается: исправить, снять заново, пройти рубрику с нуля.

### Светлая тема: ни одного серого куска

Светлые экраны ВК и ОК — одна белая поверхность: секции разделяет воздух, а не серые полосы, и группа ячеек — обычный белый список, а не вставная карточка на сером. <!-- @history --> Раньше это были белые секции на сером фоне; серые полосы между ними и серый хвост под коротким экраном разваливали композицию. Серое на белом читается как незагрузившаяся картинка или пустое место, и экран выглядит сырым. Поэтому:

- **Любой свой блок — внутри `ui.section`.** Карточка события, плеер, QR-код, положенные прямо в `ui.scroll`, выпадают из сетки отступов секций (`on-gray` в аудите). Исключение — медиа во всю ширину без текста: фото, сетка кадров.
- **Никаких серых плашек внутри белой секции** (`gray-in-white`). Карточку вещи, сети, предложения собирают строкой `ui.row` или блоком без подложки с отступом 16; вложение в посте — с тонкой обводкой `var(--ui-line)`, а не заливкой.
- **Вторичная кнопка — акцентная мягкая** (голубая в ВК, оранжевая в ОК), значок строки — на мягком акценте. Это делает ядро; концепт не перекрашивает их в серый. На тёмной поверхности внутри светлой темы (звонок, камера, таймер) концепт задаёт свою полупрозрачную белую.
- **Нет фото — нет пустого кадра.** Пост без фото — текст и вложение, без `media: 'ph'`. Человек без фото — инициалы (`initial` у истории, аватара, диалога), не `.ph`. Заглушка `.ph` остаётся только там, где кадр — суть экрана: видоискатель, медиатека, альбом.
- **Воздух:** секция 12 сверху и снизу, между действиями 12, действия отделены от содержимого секции 16. Это задаёт ядро — концепт не ужимает.
- **Сегменты, чипсы и поиск — часть шапки.** Секция без заголовка, в которой они стоят первыми, прижимается к шапке; сегмент-контрол 36 по VKUI, зона касания 44 за счёт прозрачной рамки.

## Интерфейс не объясняет сам себя

Экран показывает **данные и действия**. Он не рассказывает, как устроен продукт, и не оправдывается за свои решения. Каждая из этих фраз стояла в интерфейсе и была убрана:

> «Курс — это голос и палитра шага: видео нет намеренно» · «Права на всю медиатеку не запрашиваются и не нужны» · «Ручной ввод даёт то же, что скан» · «Now Playing заполнен: пауза и ±15 секунд работают с локскрина» · «Палитра живёт внутри проекта, а не в общем блокноте»

Признак один: **фразу произносит автор, а не продукт**. Проверка — прочитать вслух и спросить, кому это сказано. Если ревьюеру — место в `docs/06-app-store.md` (review-notes). Если читателю кейса — в доки. Если себе — вообще никуда.

Отдельно: «Ваш / Ваша / Вы» в заголовках («Ваша практика», «Ваше собрание», «Вы») ничего не сообщают. Учётной записи в концептах нет — есть номер, и в профиле стоит он.

Что **остаётся** в интерфейсе: пустое состояние при отказе в доступе, без которого фича не работает (его проверяет тест), доменное знание, без которого фича непонятна («ΔE до 2 глазом не отличить»), и правовая строка под кнопкой входа.

## Подписи списка: таблица — однородна, проза — нет

Строка данных **обязана** повторять соседнюю: «41 сторона · 1907–1928» рядом с «27 сторонъ · 1910–1924» — это таблица, и разнобой в ней был бы ошибкой. Слоп начинается там, где по шаблону написана **проза**:

> Опушки · звонкая трель · Подлесок · нисходящая трель · Кустарник · флейтовый напев

Три строки, отличающиеся одним эпитетом. Признак: подписи в списке отвечают на **один и тот же вопрос**. Лечится не переписыванием слов, а сменой вопроса — пусть каждая строка сообщает своё: одна где искать, другая чем отличается от похожего, третья что уже случилось. Заодно расходятся длины, и список перестаёт выглядеть отлитым в одну форму.

Проверка — в `npm run audit` (`formula-prose`): подписи без цифр с одинаковой синтаксической сигнатурой, три и больше в одном списке. Цифры исключены намеренно — их наличие и есть признак строки данных.

## Приложение всегда наполовину в процессе

Экран, где всё готово, ничего не грузится и всё разобрано, — это демо-случай, а не продукт. У живого приложения в любом списке смешаны состояния: скачано · скачивается 62 % · не скачано, 412 МБ · не разобран · нет в архиве · прогонов ещё не было.

Дешевле всего это добирается **разными состояниями соседних строк одного списка**, а не отдельными экранами. Индикатор в ядре — `.dl` (`.is-ready` / `.is-busy`) и `.dl-bar`.

## Плотность: экран, а не слайд

Четыре-шесть объектов по центру и одинокая кнопка внизу — верный признак сгенерированного макета. Реальный экран несёт хвост: что было вчера, что рядом, что ещё есть. Мерка грубая, но работает: **разметки на концепт меньше ~40 КБ — экраны пустые**. Было 14 КБ у «Репетиции» и 16 КБ у «Птиц» против 109 КБ у «Двора»; смотреть на «Двор».

Три частных случая:

1. **Список из трёх элементов.** Справочник на «48 видов» показывал 3 вида, история репетиций — 2 сессии. Список должен быть такой длины, какая бывает у человека, который пользуется приложением полгода.
2. **Ровные числа.** «3 метки · 2 перехода · 1 повтор» — заполненный шаблон. Живые данные неровные: 7:24, 182 МБ, +38 секунд.
3. **`.ph` как герой композиции.** Плейсхолдер — это правило, но серое поле 230×343 по центру экрана правилом не оправдано: `.ph` стоит там, где в жизни миниатюра, аватар или кадр, а вокруг — данные.

## Три ловушки CSS

Линтер и тесты их **не ловят** — только глаза на отрендеренном PNG. Все три уже случались:

1. **Класс, объявленный с нуля и в `kernel/base.css`, и в `concepts/*/styles.css`** (было `.hero`, сейчас `.btn-quiet` у «Шеллака»), молча ломает страницу. Это как раз линтер ловит — не игнорируй его сообщение про коллизию.
2. **Шорткат `background` в своём классе сбрасывает `background-image`**, который подставляет класс-носитель медиа (`.art-*`) — картинка молча исчезает, остаётся пустой блок. Писать `background-color`.
3. **Шорткат `margin` глушит утилиты `.mt*` из ядра**, потому что `styles.css` подключается ПОСЛЕ `base.css` — заголовки секций слипаются с предыдущим блоком. Писать `margin-bottom`.

## Проверки

**Прогон тестов идёт пулом.** Каждый концепт поднимает свой браузер, и последовательно полный набор занимал двадцать минут — столько никто не ждёт, и проверку начинают пропускать. Пул на четыре дорожки (переменная `LANES`) укладывается в пять минут, вывод по-прежнему идёт в порядке слагов.

**Тест выводится из спеки, а не пишется руками.** На «Петле» он сразу нашёл 5 дыр, которые ручной тест пропускал: fallback лежал на экранах, до которых при отказе не доходят.

Два правила, которые проверяет тест:

1. **Пустое состояние лежит там, куда приводит отказ.** Если `data-ask="location|yarn|project"`, то видимый `ui.denied('location')` должен быть на `project`. Для ключей без `denied` в модели тест проверяет только, что экран на месте.
2. **Проверяется каждый триггер доступа, а не первый.** Один ключ часто просят с нескольких экранов; пустое состояние нужно на каждом.
3. **Обходной вход спрашивает доступ.** Обычный переход на экран-цель `data-ask` показывает системный алерт.

**Текст, слившийся с подложкой, не ловит ничто, кроме глаз и проверки контраста.** Светлый заголовок на белой карточке внутри тёмного экрана; синяя надпись на плашке, которой переопределили фон в синий; тёмная буква на тёмном круге — все три случая лежали в сборке и проходили и линтер, и тест. `npm run audit` считает контраст, складывая полупрозрачные слои подложки; текст поверх фотографии и текст с тенью не считаются — подложки там нет.

**Неаккуратность списка — это числа, а не ощущение.** Строка-кнопка и строка-див приходят к отступу разными путями: у кнопки остаётся системный `padding`, у аватара — авто-поля из ядра, у карточки — собственный внутренний паддинг. Разница в 2–6 пикселей глазами не читается, а список из-за неё выглядит кривым. `npm run audit:grid` меряет левый край текста каждой строки и сравнивает внутри одного списка; строки со значком и без него считаются разными видами и между собой не сверяются. Горизонтальная сетка концепта одна: поле 16, значок 44, текст с 72.

**Часть дефектов не видит ни линтер, ни тест, ни беглый взгляд на PNG** — они появляются только после раскладки. Их ловит `npm run audit` (`scripts/audit-visual.mjs`): рамка агента у `<button class="row">`, шрифт мельче 11 pt, усечённый многоточием текст, выход за края устройства, хит-таргет меньше 44, подвал поверх конца списка, зависший посреди экрана tab bar, разрыв между контентом и навигацией и текстовый символ вместо нормальной иконки.

**Tab bar корневого экрана всегда стоит на физической нижней границе устройства.** Контент перед ним обязан занимать оставшуюся высоту через `flex:1; min-height:0`. Нельзя позволять высоте `main` определяться только содержимым: на коротком экране навигация окажется посередине, а под ней появится огромная пустая область. Кнопка-иконка содержит SVG из общего набора, а не временный символ `+`, `⌕`, `⋯` или `⌄`.

Самый дорогой пример: `.overview-hero h1` доставал `h1` **внутри** телефона — устройство лежит в той же сетке — и задавал заголовку экрана размер в `vw`. Кегль менялся от ширины окна, вход разъезжался с макетом, и на глаз это не читалось. Отсюда правило: **страница документа и экран устройства — разные типографические среды**; селекторы страницы скоупятся так, чтобы не доставать внутрь `.device`.

Полный цикл после любой содержательной правки, из каталога `platform/`:

```bash
npm run build -- <slug> && npm run shots -- <slug> && npm run build -- <slug> && npm run test -- <slug> && npm run lint -- <slug> && npm run audit -- <slug> && npm run audit:grid -- <slug>
```

Сборка идёт **дважды не по ошибке**: `shots` кладёт PNG в `concepts/<slug>/assets/screenshots`, а в `dist` они попадают только следующей сборкой. Без второго `build` раздел «Экраны» ссылается на несуществующие файлы, и тест валится на проверке «консоль чистая».

**Автор и критик — разные роли.** В режиме автора проверять бесполезно: видно замысел, а не результат. Проверочные фазы — циклы, а не галочки. «Выглядит нормально» — не результат проверки.

**Дизайн проверяется глазами на PNG, а не по коду.** Смотреть каждый экран в полный размер; контактный лист из миниатюр годится только для оценки общей связности.

## Ориентир

Эталон структуры — `platform/concepts/petlya/`: полный набор блоков `concept.json`, вход по номеру, 5 прототипов, доки 01–06, зелёный тест и чистый линтер. Шаблон `concepts/_template/` правила догнал: `start: "phone"`, два прототипа, блок `appStore`, все шесть доков включая `06-app-store.md`. Скаффолдиться из него можно, но структуру сверять всё равно с «Петлёй» — в шаблоне нет ни матрицы доступов на реальном наборе, ни сценарных срезов.

Но эталон — по структуре, не по медиа: см. предупреждение выше и «Известные расхождения» в README. Перед тем как копировать приём из существующего концепта, сверься с правилом здесь — правило новее.
